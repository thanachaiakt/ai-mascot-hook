# ข้อมูลเชิงเทคนิค: ใช้ทรัพยากรเท่าไร

[English](../en/technical.md)

คำตอบสั้น ๆ สำหรับคำถามว่า "ai-mascot-hook กินอะไรของเครื่องบ้าง" ส่วนแผนภาพการเชื่อมต่อของโค้ด
ดูได้ที่ [architecture.md](architecture.md)

## hook กิน token ของ Claude ไหม

**ไม่กินเลย** hook ไม่ได้เพิ่มอะไรเข้าไปใน context ของ Claude และไม่ได้เรียกโมเดลหรือใช้เน็ต

- hook แต่ละตัวคือคำสั่งเดียว `ai-mascot-hook --set <สถานะ>` (ดู `src/hooks.rs`) เขียนคำหนึ่งคำ
  ลงไฟล์ในเครื่องแล้วจบ
- Claude Code จะเอา **stdout** ของ hook ใส่เข้าไปในบทสนทนาเฉพาะบางเหตุการณ์
  (`UserPromptSubmit`, `SessionStart`) แต่ `--set` ไม่พิมพ์อะไรออกมาเลย stdout เป็น 0 ไบต์
  จึงเพิ่ม token เป็น 0
- คำสั่งจบด้วย exit code 0 และไม่พิมพ์อะไรลง stderr Claude จึงไม่เห็นข้อความ error ด้วย
  ถ้าใส่คำสถานะที่ไม่รู้จัก จะจบด้วย exit code 2 โดยไม่พิมพ์อะไรเช่นกัน
- ในโปรแกรมไม่มีโค้ดเครือข่าย ไม่มี API key ไม่มี telemetry ไม่เช็กอัปเดต

สิ่งเดียวที่ hook ใช้คือเวลา เพราะ Claude Code จะรอให้คำสั่งจบก่อนทำงานต่อ

## hook แต่ละครั้งใช้เวลาเท่าไร

| | macOS (Apple M2 Pro, วัดจริง) |
|---|---|
| รัน `ai-mascot-hook --set working` หนึ่งครั้ง | ประมาณ **5 ms** (เฉลี่ยจาก 200 ครั้ง) |
| หน่วยความจำสูงสุดระหว่างรัน | ประมาณ 8.5 MB คืนทั้งหมดเมื่อจบ |
| ข้อมูลที่เขียน | คำสถานะ (4–9 ไบต์) เขียนลงไฟล์ชั่วคราวแล้ว rename ทับ `state` |

`PreToolUse` กับ `PostToolUse` ทำงานทุกครั้งที่ Claude เรียก tool ดังนั้น tool หนึ่งครั้งเสียเวลา
ประมาณ 2 × 5 ms ยังไม่ได้วัดบน Windows ซึ่งการเปิดโปรแกรมช้ากว่า macOS แต่งานที่ทำเหมือนกัน
hook แต่ละตัวมี timeout 10 วินาที ต่อให้ค้างก็ถ่วง Claude ได้ไม่นาน

## ตอนแมวน้ำเปิดอยู่ ใช้ CPU และ RAM เท่าไร

วัดบน macOS (Apple M2 Pro) ด้วย `top` เก็บค่าทุก 2 วินาที:

| สถานะ | ท่าทาง | CPU (เทียบหนึ่งคอร์) | หน่วยความจำ |
|---|---|---|---|
| `idle` (นอนหลับ) | นอนหลับ 86 เฟรม | ประมาณ 3–6% | 16–17 MB |
| `asking` | โบกมือ 60 เฟรม | ประมาณ 7–11% | 17 MB |
| `loading` | ตบมือ (ตอนนี้ตบมือแค่ 6 วินาทีแรก แล้วนั่งคิด) 74 เฟรม | ประมาณ 7–10% | 17 MB |
| `working` | ว่ายน้ำ 95 เฟรม | ประมาณ 10–12% | 17–19 MB |

ค่าแกว่งไปมาระหว่างแต่ละรอบ ให้ดูเป็นช่วงคร่าว ๆ ยังไม่ได้วัดบน Windows
ตัวเลขนี้วัดไว้ก่อนมีท่าสติกเกอร์ (นั่งคิด ใส่แว่นกันแดด ร้องไห้ และท่าตอน idle) ซึ่งยังไม่ได้วัด
ท่าพวกนี้เล่นด้วยความเร็วเท่ากัน จากแถบภาพขนาดเดียวกัน 26–230 เฟรม จึงน่าจะกินพอ ๆ กัน
หน่วยความจำวัดเป็น physical footprint จากคำสั่ง `footprint` ตอนเปิดกล่องข้อความอยู่
ตอนสลับสถานะสูงสุด 20 MB ถ้าเปิดหน้าแก้ข้อความสถานะ จะเพิ่มอีกราว 25 MB ระหว่างที่เปิดอยู่

ภายหลังปรับแต่งบน macOS อีกรอบ (ตัวจับเวลา color space, Core Animation และแคชแบบ run
ตามรายการด้านล่าง) วัดจากเวลา CPU ที่โปรเซสใช้ในช่วง 20 วินาที หลังท่าเล่นครบรอบแล้ว ปิด auto hide
เครื่องเดียวกัน:

| กรณี | ก่อน | หลัง | หน่วยความจำหลังแก้ |
|---|---|---|---|
| `working` เปิดกล่องข้อความ | 14.5% | 0.75% | 16 MB |
| `working` ปิดกล่องข้อความ | 5.3% | 0.75% | 15 MB |
| `asking` เปิดกล่องข้อความ | 12.7% | 0.85% | 16 MB |
| `loading` เปิดกล่องข้อความ | 10.9% | 0.8% | 17 MB |
| `completed` เปิดกล่องข้อความ | | 0.9% | 16 MB |
| `error` เปิดกล่องข้อความ | | 0.7% | 15 MB |
| `idle` (นอนหลับ) ปิดกล่องข้อความ | 4.7% | 0.75% | 14 MB |

หน่วยความจำเพิ่มขึ้นราว 2–3 MB จากแคชแบบ run (ดู **หน่วยความจำ** ด้านล่าง) แลกกับ CPU
ราวหนึ่งในสามของที่เหลือ ตอนเปิดเมนูหรือหน้าแก้ข้อความ ลาก หรือปรับขนาด จะใช้มากกว่านี้ระหว่างนั้น

แอป AppKit เปล่า ๆ ที่มีหน้าต่างใสหน้าต่างเดียวก็ใช้ราว 11 MB แล้วบนเครื่องเดียวกัน
นี่จึงเป็นขั้นต่ำบน macOS ส่วนที่เหลือส่วนใหญ่คือ AppKit พื้นที่วาดของหน้าต่าง และกล่องข้อความ

ภาระมาจากตรงไหน:

- **ภาพเคลื่อนไหว:** ทุกท่าเล่นที่ 12 เฟรมต่อวินาที (เฟรมละ 83 ms) บน Windows แต่ละเฟรมถูกย่อขยาย
  ตามขนาดแมวน้ำบน CPU แล้วส่งขึ้นจอ แมวน้ำตัวใหญ่จึงใช้มากขึ้นนิดหน่อย บน macOS เฟรมถูกส่งให้
  layer ของ Core Animation ในขนาดเดิมของ PNG แล้วให้ GPU ย่อขยาย ขนาดแมวน้ำจึงไม่มีผล
  ภาพสร้างบนบัฟเฟอร์ที่ใช้ซ้ำโดยไม่คัดลอก และย้ายหน้าต่างเฉพาะตอนที่มันย้ายจริง
  (AppKit ปัดขนาดหน้าต่างเป็นจุดเต็ม จึงขอเป็นจุดเต็มตั้งแต่แรก)
- **ตัวจับเวลา (macOS):** มี `NSTimer` ตัวเดียว ทำงานที่ถึงเวลา เช่น เฟรมถัดไป การเช็กสถานะ
  กล่องข้อความ การกดค้างจนกลายเป็นลาก มันหลับจนถึงงานถัดไปแทนการตื่น 60 ครั้งต่อวินาที
  ถ้าปิดกล่องข้อความจะตื่นราว 12 ครั้งต่อวินาที ระหว่างเปิดเมนูหรือหน้าแก้ข้อความสถานะจะตื่น
  60 ครั้งต่อวินาที เพราะต้องคอยดูว่าเสียคีย์บอร์ดไปหรือยัง ซึ่งไม่มีข้อความแจ้งมา
- **สี (macOS):** ทั้งภาพที่วาดและหน้าต่างใช้ sRGB ระบบจึงแปลงสีให้ตรงจอบน GPU
  เดิมภาพเป็น device RGB ทำให้ Core Animation ต้องแปลงสีทุกเฟรมบน CPU ราวหนึ่งในสามของ CPU ที่แมวน้ำใช้
- **ตัวจับเวลา (Windows):** ใช้ `SetTimer` แยกตัวสำหรับเฟรม การเช็กสถานะ และกล่องข้อความ
  ระหว่างนั้นจึงไม่มีอะไรทำงาน
- **กล่องข้อความสถานะ (macOS):** กล่องกับฟองกลมสองลูกเป็น layer ของ Core Animation แยกกัน
  วาดครั้งเดียวตอนข้อความเปลี่ยน ตอนเด้งออก เด้ง และจางหาย ตั้งขนาดของ layer ทุก 15 ms
  พอนิ่งแล้ว การลอยและวงแหวนรอบจุดสีเป็น animation ของ Core Animation ที่วนไปเอง
  กล่องข้อความที่ขึ้นค้างอยู่จึงไม่ใช้ CPU
- **กล่องข้อความสถานะ (Windows):** ตอนกำลังขยับ (เด้งออก เด้งตอนเปลี่ยนสถานะ จางหาย) วาดใหม่ทุก
  15 ms นอกนั้นทุก 33 ms เพราะลอยขึ้นลงตลอด แต่ละเฟรมย่อขยายส่วนต่าง ๆ ด้วยเลขจำนวนเต็ม
  ที่คิดไว้ครั้งเดียวต่อแถวและคอลัมน์ และข้ามพื้นที่ใสรอบ ๆ ปิดกล่องข้อความจะประหยัดส่วนนี้
- **หน่วยความจำ:** `build.rs` ตัดภาพแต่ละท่าใน `assets/` ออกเป็น PNG เล็ก ๆ ทีละเฟรม แล้วเก็บไว้
  ใน `ai-mascot-hook.frames` ข้าง exe (ราว 12.5 MB สำหรับ 12 ท่า ไฟล์ exe ไม่ถึง 1 MB) แมวน้ำ map ไฟล์นี้
  ระบบจึงอ่านจากดิสก์เท่าที่ใช้ ไม่นับเป็นหน่วยความจำของแอป เหมือนตอนที่เฟรมฝังอยู่ใน exe ตอนรันจะถอดเฉพาะเฟรมที่อยู่บนจอ พิกเซลละหนึ่งไบต์ (260 × 260 ราว 66 KB)
  และใช้บัฟเฟอร์เดิมซ้ำทุกเฟรม บน macOS เฟรมที่วาดแล้วจะเก็บไว้เป็น run ของสีเดียวกันในพาเลตต์ด้วย
  (ท่าละราว 2–3 MB) จึงถอด PNG แค่รอบแรกของท่า run ถอดเร็วกว่าหลายเท่า และเป็นราวหนึ่งในสามของ CPU
  ที่เหลืออยู่ เวอร์ชันก่อนถอดทั้งท่าไว้ล่วงหน้า ใช้ท่าละ 6–8 MB และทิ้ง
  บัฟเฟอร์ที่ใช้เสร็จราว 25 MB ไว้กับ malloc ของ macOS ตอนนี้บน Mac จะคืนหน่วยความจำ
  ให้ระบบทุกครั้งที่เปลี่ยนสถานะด้วย (`malloc_zone_pressure_relief`)

## อ่านสถานะยังไง อ่านดิสก์ตลอดไหม

- แมวน้ำเช็กไฟล์ state ทุก **400 ms** (`POLL_MS` ใน `src/seal.rs`) แต่ละครั้งดูแค่เวลาแก้ไข
  ของไฟล์ และอ่านเนื้อหาไม่กี่ไบต์เฉพาะตอนเวลาเปลี่ยน ระบบตอบจาก file cache
  แทบไม่แตะดิสก์จริง
- บน Windows จะหาไฟล์ state ที่ถูกย้ายไปอยู่ในโฟลเดอร์ของแอปแบบ packaged (MSIX) เช่น
  Claude desktop app ด้วย แต่ไม่บ่อยกว่าทุก 5 วินาที (`RESCAN`)
- เพราะเช็กเป็นรอบ แมวน้ำจึงเปลี่ยนท่าช้ากว่า hook ได้ถึง 400 ms

## ไฟล์ที่ใช้

| ไฟล์ | ใครเขียน | เมื่อไร |
|---|---|---|
| `state` | hook | ทุกเหตุการณ์ของ hook |
| `placement` | แมวน้ำ | หลังย้าย ปรับขนาด หรือเปิดปิดกล่องข้อความ |
| `status.txt` | หน้าแก้ข้อความสถานะ | ตอนกด Save |
| `~/.claude/settings.json` และไฟล์ hook ของ agent อื่น (`~/.cursor/hooks.json`, `~/.copilot/hooks/ai-mascot-hook.json`, `~/.gemini/settings.json`, `~/.codex/hooks.json`, `~/.qwen/settings.json`, `~/.codeium/windsurf/hooks.json`, `~/.kiro/hooks/ai-mascot-hook.json`) | `--install-hooks` / `--remove-hooks` (`--agent`) | เฉพาะตอนสั่งรัน โดยสำรองไฟล์เดิมเป็น `<ชื่อไฟล์>.bak-<เวลา>` ก่อน |

โฟลเดอร์ข้อมูลอยู่ที่ `%LOCALAPPDATA%\ai-mascot-hook` บน Windows และ
`~/Library/Application Support/ai-mascot-hook` บน macOS

## วัดเองได้

```bash
# จับเวลา hook หนึ่งครั้ง (macOS / Linux shell)
time target/release/ai-mascot-hook --set working

# hook พิมพ์อะไรเข้า context ของ Claude บ้าง (ควรได้ 0)
target/release/ai-mascot-hook --set working | wc -c

# CPU และหน่วยความจำของแมวน้ำที่รันอยู่บน macOS
top -l 5 -s 2 -pid $(pgrep -f ai-mascot-hook | head -1) -stats cpu,mem
```

บน Windows ดูได้จากแท็บ Details ใน Task Manager หรือรัน
`Get-Process ai-mascot-hook | Select-Object CPU, WorkingSet64` ใน PowerShell
